# The primary runs a helper attempt as a ledger-fenced lease: renew ledger-then-helper, fail closed after submission, cancel by verified hint

`RemoteWorkerRunner` (`apps/gateway/internal/executor/remoterunner.go`, behind `UBAG_HELPER_DISPATCH`, default off) is the primary's side of one helper attempt. The primary is the gRPC client of the helper (decision D3); `internal/helperclient` dials it over mutual TLS and accepts only a certificate that chains to the manager CA, carries exactly the URI SAN `spiffe://ubag/node/<id>` of the node the placement named (a valid certificate of another node is refused), lives at most 72 h and has an SPKI that is a current or next pin in the node registry (a store error fails closed). The CN, DNS and IP SANs are never consulted: the helper is addressed by a WireGuard IP.

**The attempt is a ledger lease and nothing else can write.** A consumer asks a `HelperPicker` where a leased job runs after the lease and before assignment (ADR-0011): a placement, `ErrNoHelper` (run locally: ineligible, manager unreachable, no capacity granted) or a `HelperRetryError` (hold the job; a delayed lease Retry, never a failure and never an immediate re-queue). Any other picker error is a hold, not a local run, so a broken picker cannot move affinity-bound work onto the primary. A placed job dials and handshakes first (protocol, node id, workload version, registry digest, clock skew within 10 s: any mismatch holds the job before anything is leased), then `BeginAttempt` takes generation n+1 under a fresh attempt id, then `RunAttempt` streams the events, every one committed by the fenced `HelperIngest` (P4.9). The helper's terminal event is the job's terminal state; no event reaches the job by another route.

**Renewal order is a safety property.** Every 20 s the Attempt Lease (120 s) is renewed on the ledger first and on the helper second, and the helper is told a lease 10 s shorter than the ledger's (the skew allowance). A failing ledger therefore leaves both leases to lapse together, and the helper's own self-expiry can never outlive the ledger's: a successor attempt cannot start (the ledger refuses it) while the old helper could still be running. If no renewal succeeds for a whole 120 s the helper is declared lost. If the ledger says the attempt is no longer ours (superseded, reaped) the runner stops without writing and without cancelling anything: the job belongs to the successor, and a stale fence would be refused anyway. A fenced event that names a stale generation or another attempt while the ledger still lists the attempt as ours is the helper's fault, not a lost lease, and is treated as a lost helper.

**Loss follows the submission boundary (D4).** A broken stream is re-attached (a repeated `RunAttempt` replays from sequence 1; sequences already committed are skipped, the rest dedupe on the event key). A helper lost before `PROMPT_SUBMITTED` was read is a held job: the lease is retried after a delay and a new attempt takes generation n+1 once the old lease lapses (the runner reads the ledger first and waits for it instead of spinning). A helper lost after it, a shutdown or an unrecordable failure after it, or an earlier attempt that crossed the boundary, is `ErrAmbiguous`: the job ends `failed_terminal` with `submitted` and `reconcile_required`, the queue lease is failed and never retried, and the next attempt is refused by the ledger (`ErrAttemptSubmitted`). The boundary the runner uses is "a `PROMPT_SUBMITTED` event was read", set before the commit: the conservative side. A helper that dies before any event reached the primary but after submitting is not visible here; closing that window is the reconciler (P4.18) and a durable helper journal.

**Cancel is a hint, verified.** The cancel API calls `Dispatcher.CancelJob` first and writes the canceled status second. `NewCancelNotifier` turns a successful `CancelJob` into a wake-up for the consumer that supervises the job (`CancelRegistry`); the consumer then re-reads the store until the job is terminal (up to 3 s) before stopping the run. The hint alone stops nothing, so a cancel that failed after the dispatcher step cannot kill a running attempt. A remote attempt keeps only the 2 s store read as a safety net for a cancel written by another process; the 250 ms poll is for local runs. A stopped run sends `CancelAttempt` on a context that outlives the cancelled one, so the helper's only browser slot is not held until its lease lapses.

Decided 2026-10-06. Consequences: a job with declared attachments, a conversation, a `voice.*` command type or an `antigravity_*` target is never dispatched (the helper contract has no staging token, conversation block or viewer broker yet; those jobs run on the primary exactly as before); an attempt abandoned by a refusal or a loss holds its ledger lease until it lapses (at most 120 s), because the ledger has no explicit release; manual-action alerts and login-state projections are not raised for helper events yet; with no picker wired (`NoHelperPicker`) the flag changes nothing.
