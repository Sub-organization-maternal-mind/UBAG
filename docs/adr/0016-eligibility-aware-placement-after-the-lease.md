# Placement stays lease-then-place; a refused placement waits off the worker; the pool is sized from helper capacity

The queue API (`LeaseNext`) has no peek-by-eligibility and the file spool hands out the oldest pending envelope, so the consumer learns which Helper Node, profile and identity a job needs only after it holds the lease (the target comes from the envelope, the identity from the tenant's profile bindings). The helper placer (`nodes.Placer`, `executor.FleetPicker`, behind `UBAG_HELPER_DISPATCH`, default off) keeps lease-then-place (ADR-0011) and does not add peek-by-eligibility. Peek would change `WorkerQueue` for the file spool and NATS together (NATS has no content filter on a pull consumer), would evaluate eligibility twice with a race between the peek and the lease, and every refusal would still need the same delayed answer. What ADR-0011 left open is the head-of-line cost of a synchronous hold: a refused job holds its consumer worker for the delay, the file spool returns a retried job to the head of the queue, and one busy identity at the head starves every job behind it (with one worker, forever).

**Place after the lease and the Exec Lease, before assignment.** `FleetPicker` answers one of: a placement (a node slot and the profile's identity lane are reserved atomically; `Release` returns both exactly once); `ErrNoHelper` (run on this gateway) when no helper node is eligible at all (manager unreachable past the stale grace, nothing granted: ADR-0014 and decision D3), when the tenant has no active profile for the target (it is not on the fleet), or when a conversation cannot resume on a helper; or a `HelperRetryError` (a delayed lease Retry, never a failure and never an immediate re-queue) when the tenant has profiles but none is on an eligible node (`ErrNoMatchingProfile`: queue, never assign another tenant's or an unbound profile), when the bound node of a conversation is down (affinity: wait, never relocate), when every candidate's identity lane is busy, or when every eligible node is at its limit (`ErrNoCapacity`). A store error reading the fleet or the profiles is a hold too, never a local run. The identity lane key is the `profile_ref`: one active operation per physical session (D6), and one tenant's busy session never blocks another's. The helper's own admission stays the backstop: slot and lane counts live in this process, so a second primary replica, or a helper that is busier than this process knows after a restart, is refused by the helper and held back by the runner (ADR-0014); the fleet supports one primary replica until the lanes move into the shared admission store.

**A refused placement waits off the worker.** With `UBAG_HELPER_DISPATCH` on, the consumer hands a held lease to a goroutine that retries it after the delay (2 s for placement holds, at most 30 s) and returns the worker at once, so the next job is leased immediately: a busy identity neither pins a worker nor blocks a runnable job behind it, and the held job is leased and placed again once per delay, not once per poll. At most 64 leases wait this way; past that bound the hold is synchronous (the previous behaviour), which bounds both the leased backlog and the placement churn per delay. A held lease is not heartbeated (the same exposure as ADR-0011, bounded by the 30 s cap and the 30 s minimum queue lease TTL); shutdown retries every held lease before `Run` returns. On NATS each hold is a `NakWithDelay` that consumes a delivery (`UBAG_NATS_WORKER_MAX_DELIVER`, default 5), so a NATS deployment that enables dispatch must raise it.

**The pool is sized from capacity.** With dispatch on, the worker count is the local pool (`UBAG_WORKER_CONCURRENCY`, clamped to 32 as before) plus the sum of the admission limits of the eligible helper nodes (min of the manager grant and the ceiling table, pressure- and ramp-adjusted), bounded at 512, instead of the clamp of 32: every remote attempt occupies one worker for its whole run. The count is re-read every 15 s and only grows (an idle worker parks in the idle poll backoff; the placer, not the pool, bounds helper work). Because extra workers must not raise local concurrency, a gate of the local pool size admits local runs; a job that finds it full is held like any other refused placement.

Decided 2026-10-06. Consequences: a tenant with helper profiles whose nodes are all down waits (bounded only by the job's own timeout and the stale-job reaper) instead of silently using the primary's own browser session, except when the whole fleet is ineligible, which follows ADR-0014 and runs locally; there is no create-time overload yet (a deep backlog of held jobs is visible only in `ubag_helper_placements_total{outcome}` and the logs); peek-by-eligibility remains the right answer if the held backlog ever needs to exceed the bound, and needs the queue API change.

Status: accepted
