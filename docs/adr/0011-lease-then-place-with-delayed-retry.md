# Lease-then-place: a placement refused after the lease is a delayed Retry

The worker consumer leases a job from the queue first and learns which warm-daemon slot and which identity it needs second, because the queue API (`LeaseNext`) has no peek-by-eligibility and the file spool hands out the oldest pending envelope. A placement that fails after the lease can therefore busy-loop: the file spool's `Retry` re-queues instantly and wakes the poller, so lease, refuse, `Retry`, lease repeats at poll speed. For the local Daemon Pool (`UBAG_WORKER_POOL_SIZE` > 1) we accept lease-then-place with these rules: the pool places the job after the lease with a bounded wait (`UBAG_WORKER_POOL_WAIT_MS`, default 30 s) behind a bounded placement queue (the pool size), keeping one active job per physical session; on saturation it returns the typed retryable `ErrPoolOverloaded`; the consumer answers that with a delayed `Retry` (release the Exec Lease, hold the lease for the overload's retry-after, 2 s by default and 30 s at most, then nack it). It is never an ack, never a failed job, never an immediate re-queue; the job's status stays `assigned` because it never ran. A pool of one slot behaves like the single warm daemon of today, and `UBAG_WORKER_CONCURRENCY` is raised to the pool size so every slot has a consumer worker to feed it. Decided 2026-10-06 as the interim for P3.6; the helper placer (P4.17) supersedes it with eligibility-aware leasing, because peek-by-eligibility needs a queue API change that belongs with the helper plane. Known limits: a burst of jobs for one busy identity at the head of the queue still pins up to pool-size consumer workers until it drains (the order is the same as today's serial consumer, so it is not a regression); and on NATS every overload `Retry` is a `NakWithDelay` that consumes a delivery (`UBAG_NATS_WORKER_MAX_DELIVER`, default 5), so a NATS deployment that enables the pool must raise either that or the pool wait.
