Status: **partial**. Tooling, runbook and offline tests are merged. **No baseline was measured and no numbers are claimed**:
the exit gate needs an isolated Linux stack with cgroup limits (D5: not the Windows dev box, never the shared VPS), and none
exists in this environment. The VPS headroom snapshot likewise needs the P0.1/P0.2 read-only probe, which this slice may not run

## What it does
`run` drives `tests/load/acceptance.mjs` (mock target) through: ladder 1/2/5/10/20 (`clients-100 --clients N --iterations 3`, N
concurrent clients as the proxy for "concurrent workloads"; same steps as `workloads/mixed.json`), `clients-100` (100 clients),
`queue-1000`, `events-latency`, and a 30 s `steady-state`. Pass `--containers gateway=..,browser=..,worker=..` for cgroup
CPU/throttle/memory/OOM sampling (P0.10). Output goes to `tests/load/results/baseline-<ts>/` (git-ignored): `baseline.json`,
`baseline.md`, plus each step's full harness `report.json` (with `meta.provenance`: gateway commit, harness SHA, host spec, env knobs,
container limits).

Guards: loopback/private `UBAG_LOAD_BASE_URL` only; `UBAG_LOAD_ALLOWED_HOSTS` is stripped from the child env so the harness host guard
cannot be widened through this tool; `--i-understand-this-is-load` is required. Every baseline is labelled
`NON-AUTHORITATIVE` unless run on Linux with `--isolated-lab-host` (an operator assertion, not something the tool can verify).

`budget` computes the P3.6 pool-size cap from a baseline, per container role:

```
extra_slots = min( floor((limit*(1-h) - peak) / slot_cost),                       # container cgroup
                   floor((host_MemAvailable - h*host_MemTotal) / slot_cost) )     # only when --vps-snapshot is given
pool_cap    = current_slots + extra_slots          # h = 0.20; peak was measured with current_slots (1 in production)
```
`--vps-snapshot` is a small JSON `{ "mem_total_mib": N, "mem_available_mib": N }` transcribed by the VPS owner from the P0.1 probe
(not committed). An unlimited/unsampled container, a missing slot cost, or a missing peak yields `pool_cap: null` and exit 1 (fail closed).

## Runbook (isolated Linux Docker stack only)
```
# stack: docker-compose.small.yml profile on an isolated Linux host, memory/cpu limits like production (the limits in `docker-compose.vps.yml`)
export UBAG_LOAD_BASE_URL=http://127.0.0.1:8080 UBAG_LOAD_API_KEY=<throwaway key>
node tools/perf/baseline-matrix.mjs run --i-understand-this-is-load --isolated-lab-host \
  --containers gateway=<gw>,browser=<br>,worker=<wk>
# slot cost: apps/worker/tests/bench/measure_slots.py (stub) or tools/perf/helper-footprint.sh (real Chrome)
node tools/perf/baseline-matrix.mjs budget --baseline tests/load/results/baseline-<ts>/baseline.json --role <role> \
  --slot-cost-mib <measured> --vps-snapshot vps.json
```
Then record numbers, gateway commit SHA, host spec and the caveats below in the P8.1 consolidation (PROGRESS.md is not edited here, rule 10).

## Caveats to carry with any number
- The mock target bypasses the warm daemon, browser and provider cost; it says nothing about those (stub slots under-count a real slot).
- The 60-minute steady-state and the 20-workload lab ladder need the lab host (D5); the 30 s steady-state here is a smoke only.
- `--clients N` is a proxy for N concurrent workloads, not N real browser sessions.
- Which cgroup holds the worker slots (gateway vs browser container) is not established here: pass the right `--role`.
