# P0.16 - Real-Chrome helper-footprint spike harness

Status: merged (tooling + doc only). Not run: no Linux Docker host in this environment. No numbers claimed.

## Files
- `tools/perf/helper-footprint.sh` (new). Flags: none. Migrations: none.

## What it does
Runs one real headless Chrome (about:blank, throwaway profile, no provider page, no login: safe-mode) plus the
P0.8 `measure_slots.py` worker slots inside a container limited like the helper ceilings, and samples the container
cgroup v2 once per second: `memory.current`, `memory.peak`, CPU usec, `nr_throttled`, `throttled_usec`, OOM kills.

| Profile | Helper size | docker limits |
|---|---|---|
| `2c4g` | 2 vCPU / 4 GiB | `--cpus=1.5 --memory=2560m` (1.5 CPU / 2.5 GiB) |
| `4c8g` | 4 vCPU / 8 GiB | `--cpus=3 --memory=5g` (3 CPU / 5 GiB) |

## Run (Linux Docker host only; never the shared VPS)
```
docker build -f deploy/small/browser-viewer/Dockerfile -t ubag-browser-viewer:footprint .
tools/perf/helper-footprint.sh -p both -s 60 -n 2 -o ./footprint-out
```
Non-Linux or no Docker: the script prints SKIP and exits 0. Output: `<profile>.csv`, `<profile>.err`.

## Reading the result (thresholds are proposals, not measured)
- OOM kill > 0 or `peak_mem_current` >= 90% of the limit: the ceiling does not hold this slot count; reduce slots or raise the helper size.
- `nr_throttled` growing steadily with `throttled_usec` above ~5% of wall time: CPU-bound at the cap; the 75% CPU headroom assumption fails.
- Stub worker slots measure protocol overhead only (~17 MiB/slot, P0.8); add real-slot runs on the lab host for provider timings.
- Laptop/Docker Desktop numbers are NON-AUTHORITATIVE (D5); authoritative runs need the isolated lab host.
