# P1.2 - Per-job event wake hub replacing 50 ms SQL polling (local mode)

Status: merged (see PR). Flag default OFF, so production behaviour is unchanged until `UBAG_EVENT_NOTIFY=local` is set.

## What changed

- `apps/gateway/internal/jobs/notify.go`: in-process `eventHub` (job id -> set of cap-1 wake channels, non-blocking lossy send, the same pattern as the file-spool enqueue channel), `waitEventsLoop` (shared SQL-store WaitEvents body), `jitteredFallback` (+0..20%), `ParseEventNotify`, `DefaultEventFallbackInterval` (2 s).
- `sqlite.go` / `postgres.go`: `EnableEventNotify(fallback)`; `WaitEvents` now delegates to `waitEventsLoop`; `wake.notify(jobID)` runs only after a successful `tx.Commit()` at the four event-writing sites per store (`Create`, `TransitionStatus`, `UpdateStatus`, `ApplyWorkerEvent`). `notify` on a nil hub is a no-op, so the flag-off path is the legacy 50 ms poll byte for byte.
- `serve/serve.go`: `configureEventNotify` applies the env flags when the SQL job store is built.
- Tests: `jobs/notify_test.go`, `serve/event_notify_env_test.go`.

## Flags

| Flag | Default | Meaning |
|---|---|---|
| `UBAG_EVENT_NOTIFY` | `off` | `off` = legacy 50 ms poll; `local` = wake hub. `postgres` (LISTEN/NOTIFY) is reserved and NOT built: it, like any unknown value, logs a warning and stays on the legacy poll. |
| `UBAG_EVENT_FALLBACK_MS` | `2000` (only read when `local`) | Jittered safety-net poll. Must be a positive integer, else startup fails fast. |

Migrations: none.

## Correctness notes

- Subscribe happens inside `WaitEvents` BEFORE the first `listEvents` read, so a commit between read and wait leaves a pending wake (tested: `WakeBeforeFirstReadIsNotLost`). `WaitEvents` is called by the SSE, gRPC and facade handlers only after the job was loaded through the scoped getter, so the hub (job ids only, no data) is reached only post-auth.
- Unregister is `defer`red; the hub spawns no goroutines.
- The hub sees only this process's writes. With a shared Postgres and several gateways, another gateway's event is picked up by the fallback poll (<= ~2.4 s). That is the cost of `local`; the `postgres` mode would remove it and is deferred.
- Wake latency is bounded by SQLite/Postgres read time after the notify, not by a timer.

## Checks run

- `gofmt -l`, `go vet ./internal/jobs ./internal/serve`: clean.
- `go test -race -count=1 ./internal/jobs`: pass (includes P1.1 `waitEventsContract` on memory and sqlite with the flag off, and sqlite again with the flag ON via `TestSQLiteStoreWaitEventsContractWithWakeHub`).
- `go test -count=1 -run TestConfigureEventNotify ./internal/serve`: pass.
- Hub tests: wake within 10 ms, only matching job woken, 1k waiters across 100 jobs wake only the matching 10, lossy cap-1 never blocks, cancel/unsubscribe leaks no entries or goroutines, dropped notify (write by an un-hubbed store on the same DB) recovered by fallback, idle waiters read at the fallback cadence (20 idle waiters / 600 ms: hub <= 120 reads vs legacy >= 5x more).

## Checks NOT run

- Postgres suite (`postgres_wait_events_test.go`, env-gated, needs a database) was not run; the Postgres store shares `waitEventsLoop` and the identical notify sites but has no flag-on test of its own.
- Off-vs-local A/B on an isolated stack via the P0.12 events-latency scenario: not run (no isolated stack, D5; never aim load at the shared VPS). When run, label numbers NON-AUTHORITATIVE and record which flags were on.
- Real `database/sql` driver query counter: the idle-load evidence above counts reads at the `waitEventsLoop` read callback (one `listEvents` = one existence query + one select), not driver statements.
- The "about 4,000 queries/s for 100 idle streams" figure in the roadmap is an unmeasured arithmetic estimate; it is not confirmed here.

## Deviations

- MemoryStore is unchanged. Its `WaitEvents` is already push-based (`sync.Cond` broadcast on every append, no DB, no timer), so a hub would add risk for no DB/CPU gain. The "all three stores" wording in the spec is satisfied in effect: the memory store never polled. Cost: its broadcast wakes all waiters on any job, which is cheap in-memory.
- `postgres` mode value: warn-and-stay-off rather than a hard startup error, so a typo or early adoption of the reserved value cannot take the gateway down.
