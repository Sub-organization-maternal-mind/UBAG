## Containerised run (workflow `helper-isolation.yml`, NOT run)
`go-isolation` job: the Go suites plus the Python checks, on Linux. `containers` job: builds `deploy/helper/Dockerfile`, issues throwaway certs with
`TestIsolationWriteFixtures` (48 h, only on the runner), starts two containers (`iso-a`, `iso-b`) with the manifest's hardening (non-root, read-only
root, no caps, no-new-privileges) on a private network at fixed addresses, then runs the Go container test as the primary and the Python scans:
every process environment in each container (`/proc/*/environ`, PID 1 must show `UBAG_HELPER_NODE_ID` so the scan is not vacuous), distinct node ids and
no shared mounts, and refusal to start with a primary secret in the environment without echoing the value.

What I could verify without Docker: the Go container test was run against two native `ubag-helper` processes (built from `cmd/ubag-helper`, the real
Python worker daemon, real mTLS, certificates from the fixture writer, loopback addresses) and passed at 1, 2, 5 and 10 workloads; the refusal test was
run against the native binary and passed. The workflow YAML, `docker run` flags, the Dockerfile run-time behaviour (read-only root, tmpfs, uid 10001
reading the mounted keys), container networking and the `/proc` scan were not run.

## Findings and caveats
- **A real worker cannot complete a job without a provider.** The helper image's worker has no mock adapter (`no live selector configuration for target
  'mock'`), so against containers the jobs end `failed_retryable` through the real path. The container test therefore asserts isolation and exactly-one-
  result for any terminal outcome and does not check that the result echoes the prompt. The scripted in-process suites cover the success path. A
  synthetic provider inside the container (`UBAG_SYNTHETIC_PROVIDER`, `synthetic_chat`) would let the container run complete jobs; it is not in the image.
- **The ledger fence is not a clock.** A lapsed lease is enforced only when a successor begins or the reaper expires it (documented on
  `Attempt.LeaseExpiresAt`). The post-submission case therefore calls `ExpireAttempts` (what `StaleJobReaper` does in production) before the late write.
  An un-reaped, unsuperseded holder can still land finished work until then; that is the ledger's documented design, not a regression.
- **One helper admits at most 8 attempts** (`maxAttemptsCeiling`), so 10 and 20 workloads need two and three helpers. An earlier draft that sent 10
  jobs to one helper was refused with `helper at its attempt capacity`.
- A helper keys its attempt records by job id: a test that reuses job ids against long-lived helpers (a fresh store per subtest) gets `stale lease
  generation or attempt_id mismatch`. The container test uses one store for the whole run.

## Deviations
- The spec's `tests/chaos/tests/test_helper_isolation.py` exists, but the Go integration test is in `internal/helperclient` (and `internal/helper/runner`
  for the env dump), not `internal/helperauth/isolation_integration_test.go`: the reusable real-helper rig (`newRig`) and the primary's dial live in
  `helperclient`'s tests and `helperauth` cannot import them without a cycle.
- `tests/load` is unchanged: the P7.2 ladder already covers the gateway-level tenant probe and duplicate-result counters; this slice covers the helper
  plane the load harness does not reach.
- No chaos experiment JSON was added (the P4.14 experiments are definitions only); the Python file checks the Go tests and the workflow instead.
- Artifacts: no helper attempt carries attachments today (dispatch keeps them local), so there is no helper-side artifact path to leak through; the
  suites assert no tenant or app id and no foreign marker in what a helper receives and in every stored result.
