# P4.13 - Read-only provider readiness probe

Status: merged (worker side). Gateway/helper consumption of the probe is out of scope (P4.x helper plane).

## What landed

- Protocol v2 `probe` control line may now carry `payload` (a DispatchEnvelope naming target / tenant / profile).
  Without `payload` it stays the pure liveness query from P3.4 (`state: idle`, browser never touched).
- With `payload` the daemon (`WarmWorkerDaemon.probe_readiness`) reuses `driver.open` and `driver.detect_login_state`
  only. It never calls `submit_prompt`, `fill`, `await_manual_login` or anything that types; logins stay human-only.
- Reply adds `target`, `login_state` (`authenticated|login_required|unknown`), `selector_version`; plus `state: busy`
  (no `login_state`) when the physical-session identity is held, `cached: true` for rate-limited repeats, and
  `error: readiness_probe_failed` (generic, no exception text) for an unusable payload / unknown target.
  Selector drift and driver errors map to `login_state: unknown`.
- Identity lock: `IdentityLock(key, blocking=False)` raises `IdentityBusy` instead of waiting. The probe takes it
  non-blocking in slot mode (same auto-on rule as jobs), so it can neither overlap a job nor delay one.
  On Windows the lock is a no-op (unchanged).
- Rate limit: repeat probes of one identity within `UBAG_WORKER_PROBE_MIN_INTERVAL_S` (default 30, `0` disables)
  are answered from the previous reply with `cached: true`. `busy` is never cached.
- A warm page for the identity is reused (and left warm); otherwise a cold driver is opened and always closed.
- Host health stays separate: the probe reports provider/session readiness only.

## Flags / migrations

New env knob: `UBAG_WORKER_PROBE_MIN_INTERVAL_S` (default 30). No other flag: v2 is opt-in per request line, and
a readiness probe only happens when a sender explicitly sends `probe` + `payload`. No migrations.

## Sender obligations (documented in the schema)

Never send a readiness probe while an operator login or viewer session is active; the daemon cannot see that.

## Deviations

- Spec listed a `probe` request type; implemented as an extension of the existing `probe` control (optional `payload`) instead of a new
  control kind, keeping the control enum and v1/v2 compatibility rules unchanged.
- "Waits/returns busy": chose return-busy (non-blocking) so a probe never queues behind a long job.
