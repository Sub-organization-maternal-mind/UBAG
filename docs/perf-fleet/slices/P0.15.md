## The traced path (facts, all verified in source at the branch tip)

"Uploaded audio" is not a separate feature. It is a job with an attachment of kind `audio` or `voice`. UBAG never transcribes anything itself: the provider's web UI (ChatGPT, Gemini, Le Chat) listens to the file and the gateway returns whatever text the provider wrote. There is no Whisper, no ffmpeg, no audio decode anywhere in the gateway or worker.

1. Entry points (three, all end in the same artifact store + dispatch gate):
   - Native multipart one-shot: `POST /v1/jobs` with `multipart/form-data` (`httpapi/server.go` `handleJobs` -> `createJobMultipart` in `httpapi/attachments_gate.go`). First part must be the `job` JSON envelope; one file part per declared attachment, field name = attachment key.
   - Native two-step: `POST /v1/jobs` (JSON, declares `input.attachments[]` or the legacy `input.audio_artifact_key`) creates a HELD job (`created`), then `PUT /v1/jobs/{id}/artifacts/{key}` per file (`putJobArtifact`).
   - OpenAI facade: `POST /v1/openai/audio/transcriptions` (`httpapi/openai_facade.go` `handleOpenAITranscription`, the OET path) and `input_audio` parts of `/v1/openai/chat/completions`. The transcription route builds a held job with kind `voice`, a fixed "Transcribe the attached audio verbatim" prompt, stores the bytes server-side and waits for the job. Model `whisper-1` or blank maps to `chatgpt_web`.
2. Validation at create time (`validateAttachmentsForCreate`, `attachments.DeclaredAttachments`): max 32 declared attachments (schema ceiling), kinds `document|image|audio|video|voice`, single-path-segment keys, content type must be accepted by the TARGET ADAPTER's `manifest.json` `attachments` block (fail closed: no block => `UBAG-VALIDATION-ATTACHMENTS-UNSUPPORTED-001`). Per-adapter policy (read from manifests, cached per target):

   | Adapter | Audio/voice accepted | Max files / per-file bytes |
   | --- | --- | --- |
   | chatgpt_web, gemini_web, mistral_lechat | `audio/webm, audio/wav, audio/x-wav, audio/mpeg, audio/mp4, audio/ogg` (kinds `audio` and `voice`) | 10 / 32 MiB |
   | deepseek_web, duckai_web | none (documents + images only) | 10 / 32 MiB |
   | mock, generic_chat, generic_form, antigravity_cli, antigravity_sdk | no `attachments` block => attachments rejected | n/a |

   The JSON batch route (`/v1/jobs/batch`) rejects attachment jobs outright.
3. Bounds and admission: the JSON envelope is limited by `MaxBodyBytes` (default 1 MiB). Per file: `min(manifest max_file_bytes, 32 MiB artifact ceiling)`; the multipart total cap is `max_files x per-file` (320 MiB for the three audio providers). The transcription route caps audio at 24 MiB. The artifact PUT path takes a Content-Length reservation from the shared 256 MiB in-memory upload budget (`reserveUploadBytes`, 503 `UBAG-OVERLOAD-UPLOAD-001` + Retry-After on refusal) and then `io.ReadAll`s the whole file into memory (up to 32 MiB per request). The facade transcription route reserves `(24 MiB + maxBody) x 2` and buffers the file. The multipart one-shot streams each part to a bounded temp file (`os.CreateTemp`, sha256 computed while staging) and does NOT call `reserveUploadBytes`.
4. Storage: bytes go to the artifact store (`UBAG_ARTIFACT_STORE`, default `memory`; `localfs` or `minio` when configured; the production value was not probed by this slice). The artifact record exposes `key`, `content_type`, `size_bytes`, `checksum` (hex sha256) through `GET /v1/jobs/{id}/artifacts`. Memory/localfs stores compute the sha256 of exactly the stored bytes.
5. Dispatch gate: a job that declares attachments is born HELD (`created`) and holds its concurrency token. It is enqueued only when every declared key exists (`maybeDispatchAfterArtifact`, CAS `created -> queued`, exactly one winner). Multipart one-shot stores all staged files first, then dispatches (job is born complete, response 202). A sweeper (`RunAttachmentSweeper`) fails jobs held longer than 10 minutes (`attachmentUploadTTL`) and deletes their partial artifacts. Uploaded bytes become immutable after dispatch (409 `UBAG-VALIDATION-ATTACHMENT-IMMUTABLE-001`). A crash between the CAS and the outbox append is repaired by `recoverQueuedAttachmentOutbox`.
6. Executor to worker: the envelope that is spooled or sent to the worker carries only the attachment MANIFEST, never bytes. At run time the gateway-side runner (`executor/workerconsumer.go` `materializeAttachments`, used by both `ProcessWorkerRunner` and the warm-daemon runner in `daemonrunner.go`) streams each artifact into `os.MkdirTemp("ubag-attach-*")/<filename>` (mode 0600) and injects `input.attachment_local_paths` (declared order) plus `input.audio_local_path` for the legacy single-audio alias. Temp files are removed by a deferred cleanup. Failures are counted in `ubag_attachment_materialize_failures_total{reason}`. There is no latency metric for this copy.
7. Worker (`apps/worker/ubag_worker/live/envelope.py`, `engine.py`): the envelope parser accepts a local path only if it resolves inside a `ubag-attach-*` directory under the system temp dir. The engine re-checks kind/content-type pairs, REFUSES to submit (`blocked: attachment_not_supported_by_target`, non-retryable) when the adapter has no `file_input` selector or no materialized path, then calls `driver.attach_files` (Playwright `set_input_files` on the provider's hidden file input, or the file-chooser walk for Gemini), emits a `file.attached` event and submits the prompt. A drifted file input raises the existing drift error. The step is timed as the `attachment_materialize` stage (P0.9b timings) even though it is the browser attach, not the gateway copy.
8. Provider: the audio is handed to the provider UI as an ordinary file upload; the provider decides how to handle it. Completion is the usual streamed text of the chat turn. The registry stub path (adapters other than live providers) ignores attachments.

## Gaps and risks found (none fixed here; this slice is facts + harness)

1. `mock` cannot carry attachments (no `attachments` manifest block), so uploaded audio cannot be load-tested against the fast mock path, and the mock bypasses the warm daemon anyway. A measurable audio workload needs either a real provider session (operator login, human accounts, not automatable at load) or a test adapter that declares an attachments policy and a driver that accepts files. Without one, the 5-20 uploaded-audio workload target is unmeasurable in CI.
2. Real providers are capped by identity (D6): one active operation per (provider, physical session). An audio job occupies that identity for the whole upload + provider-processing time, which for long audio is the dominant cost, and no number for it exists.
3. Memory and temp-disk accounting is uneven: the PUT and transcription routes buffer whole files in the Go heap (bounded only by the 256 MiB shared budget and `GOMEMLIMIT=950MiB` in production); the multipart route bypasses that budget and writes up to `max_files x 32 MiB` of temp files per request with no aggregate cap. Concurrent multipart uploads can fill the temp directory (which is also where `ubag-attach-*` materialization writes) before any limiter notices. Not measured.
4. Materialization copies every attachment artifact -> temp file inside the gateway container on each run (and again on every retry of the job). The Python worker also runs in that container, but Chrome is in the separate browser container reached over CDP. Whether Playwright `set_input_files` over a remote CDP connection transfers the file contents (as opposed to a path the browser container cannot see) was NOT verified in this slice: it needs a live check on the real topology (P0.16 style) before anyone trusts audio on the production layout. The helper-plane (P4) design must also stage attachments to the helper explicitly; today the path assumes gateway and worker share a filesystem.
5. No latency or size metrics for the attachment path: only `ubag_attachments_total{kind,outcome}`, dispatch-failure and materialize-failure counters. Upload accept time, materialize time and attach time are invisible in Prometheus; only the worker `attachment_materialize` span (browser attach) exists in job timings.
6. Retention: uploaded audio stays in the artifact store after the job ends; the source comment mentions an "artifact GC" but no retention/GC job was found in `apps/gateway`. For user audio this is a privacy and disk-growth question to settle (follow-up, not changed).
7. The OET-facing transcription route has no harness coverage yet (the new scenario drives the native multipart route). Its timeout behaviour (`facadeMaxWait`, 504 `wait_timeout`) for long recordings is untested.
8. `audio` vs `voice`: manifests accept both for the same MIME types, the legacy `audio_artifact_key` folds to `audio`, the facade uses `voice`. Behaviour is identical downstream; only the metrics label differs. The workload uses `audio`.
9. The synthetic fixture is a tone, not speech. It proves transport, storage and attach integrity, not transcript quality.

## Workload manifest and harness

- `tests/load/workloads/audio-upload.json`: route `native_multipart`; target requirement = adapter accepting `audio/wav` as `audio` or `voice` (suggested chatgpt_web, gemini_web, mistral_lechat); fixture generator `synthetic-wav` (16 kHz mono 16-bit PCM tone) with profiles `short` 5 s (160,044 B), `medium` 120 s (3,840,044 B), `large` 780 s (24,960,044 B, under the 24 MiB transcription cap and the 32 MiB artifact ceiling); `max_bytes` 24 MiB.
- Schema check (`validateWorkload`): JSON-schema subset (type/const/enum/required/properties/additionalProperties/items/minItems/minimum/maximum/minLength/pattern) plus cross-field rules (default profile exists, every profile fits `max_bytes`, fixture type/kind are listed in the target requirements). `loadWorkload` throws on any error so a bad manifest cannot run.
- Scenario `audio-upload` (opt-in, excluded from `--scenario all`): `--audio-jobs` multipart creates through the existing retry/backoff logic (`audio_create` op), then per job lists artifacts and requires key present, `size_bytes` equal and `checksum` equal to the fixture sha256 (`audio_upload_violations` otherwise), then `settleJobs` (poll to terminal, result and event verification, tenant probe, as every other scenario). A 4xx create (target without an audio policy, content type refused) is a violation, not an inconclusive. Threshold `max_audio_upload_violations: 0`.
- Not done on purpose: text/attachment/mixed/voice manifests and report provenance (P0.11), the 1/2/5/10/20 ladder (P7.2), a harness path for `/v1/openai/audio/transcriptions`.
