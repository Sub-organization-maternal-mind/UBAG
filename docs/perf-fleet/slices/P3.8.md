# P3.8 - Python incremental engine streaming: pre-submit buffered, post-submit live

Status: merged (Python worker only; flag default OFF; no Go consumer reads incrementally yet, that is P2.2 apply).

## What landed
- `apps/worker/ubag_worker/live/engine.py`
  - The interaction body (`_run_interaction_inner`) is now a generator, `_interaction_steps`, that yields `(type, data)` pairs and returns the `blocked` descriptor. The buffered path (`_run_interaction_inner`, unchanged contract) just drains it into the list, so flag-off behaviour is the same code path as before.
  - New `_streamed_interaction` (used only with `UBAG_WORKER_STREAM_EVENTS`): events produced before `submit_prompt` returns (new chat, config, attach) are held; if the interaction fails before submit they are dropped and the interaction retries up to 3x exactly as before (no duplicate events). The moment submit returns, the held events are flushed, `prompt_submitted` is yielded, and everything after is yielded live: tokens reach the consumer before `read_final_response` runs.
  - Never resubmit: after submit, an ordinary exception becomes terminal `failed_terminal {submitted:true, retryable:false, reconcile_required:true, stream_end_reason:"error", reason:"post_submit_failure", current_thread_url?}` (shared `_post_submit_failure` helper, also used by the P3.2 buffered path). Drift / manual-action / `LiveSessionError` keep their existing handling (post-submit drift is `blocked`, never a retry).
  - Streaming implies the strict-submit marker: `prompt_submitted` is emitted when either `UBAG_WORKER_STREAM_EVENTS` or `UBAG_WORKER_STRICT_SUBMIT` is on.
  - After the terminal event the thread bind is best-effort in streaming mode (a `current_thread_url` failure can no longer produce a second terminal event); the buffered path keeps propagating as before.
  - Token cap: gateway rejects a run of more than 512 events and the live driver can emit one token event per ~0.4 s poll. Under the flag, token events are bounded by `UBAG_WORKER_STREAM_MAX_TOKEN_EVENTS` (default 400); further deltas coalesce into ONE trailing token event before the terminal event. `metadata.token_count` still counts deltas. The tail is not live (see follow-ups).
- `apps/worker/ubag_worker/live/daemon_protocol.py`: the v2 `hello` reply advertises `stream_events` only while the flag is on (P3.4 had left it out until this slice). The docstring records that JOB_END, not the terminal event, ends the stream.
- Event ids: nothing new. `emit()` already stamps `data.attempt_id` / scopes ids from `payload.attempt.id` (P3.7); the new tests pin that ids differ across attempts and are stable within one on the streamed path. Pre-submit retries do not burn sequence numbers because held events only get a sequence when flushed.
- `apps/worker/tests/test_stream_events.py` (+ `tests/golden/stream_events_flag_off.json`, captured from the engine at the tip before this slice, `created_at` stripped).

## Flags
- `UBAG_WORKER_STREAM_EVENTS` (Python worker), default OFF. Off: byte-identical (golden test, three scenarios: plain, attempt-scoped, conversation bind).
- `UBAG_WORKER_STREAM_MAX_TOKEN_EVENTS` (tunable, default 400, only read when the flag is on).
- Pair with `UBAG_WORKER_ATTEMPT_EVENT_IDS` on the gateway: without an attempt id, a redelivered job re-emits legacy `job:seq` ids that collide with events already ingested from the abandoned attempt.

## Ordering contract for consumers
`queued, session.opening, session.authenticated, running, [topology], [new_chat, configured, file.attached], prompt_submitted, token*, <terminal>, [conversation.thread_*], [concurrency.cap_changed], JOB_END`. Telemetry follows the terminal event, so a reader must stop at JOB_END (daemon) or EOF (cold runner), not at the first terminal event. Token events are provisional; only a terminal event carries a result.

## Migrations
None. No contract change (`prompt_submitted`, `submitted`, `reconcile_required`, `partial`, `attempt_id` already in job-event.schema.json; `stream_events` already in the worker-daemon-job-end features enum).

## Deviations
- The work item listed `events.py`, `envelope.py` and `daemon.py`: none needed a change (attempt scoping already existed in `events.py`; `envelope.py` ignores the attempt block; the warm daemon already discards the driver after any non-completed job and on `GeneratorExit`). The only daemon-side change is `daemon_protocol.py` (hello feature).
- `UBAG_WORKER_STREAM_MAX_TOKEN_EVENTS` is a new tunable beyond the spec, added because the work item's own risk note (512-event gateway cap at ~2.5 events/s) would otherwise be hit by long reasoning streams. The buffered path is left unbounded on purpose (byte-identical).
- Streaming implies the strict-submit behaviour instead of requiring both flags: there is no safe streaming without the never-resubmit rule.
- chat-ledger recording and the thread bind now run after the terminal event has been sent; if the consumer abandons the stream right after `completed` (daemon deadline race) the ledger entry for that chat is skipped (worst case one chat is never reaped, same trade-off the sink already documents).

## Follow-ups
- P2.2 apply: incremental `ApplyWorkerEvent` with a provisional/terminal barrier and per-attempt budgets (then the coalescing tail can be removed or raised); the consumer must treat JOB_END as end of stream.
- P3.5: Go `daemonrunner` should read the `hello` features and only expect live lines when `stream_events` is advertised.
- Turn the flag on only together with `UBAG_WORKER_ATTEMPT_EVENT_IDS`, after a human verifies the live DOM.
