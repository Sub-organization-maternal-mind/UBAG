# P4.21 Grant shrink / drain policy, 1-to-N ramp rule, host-pressure telemetry source

Status: merged into `feat/perf-fleet`. Size M. Depends on P4.1, P4.4 (merged). Pure logic plus ADR; no wiring, no flag, no migration.

## Files

- `apps/gateway/internal/nodes/drain.go`: `ShrinkCap(target, usage)` (cap = max(target, active), free = max(target - active, 0)); `PlanDrain(state, usage, drainStart, now, grace) DrainPlan`. Drains only for `draining`/`revoked`; `CallDrain` + `GraceSeconds` for the Drain RPC; `CancelNonVoice` only after grace elapsed since a known `drainStart` and only when non-voice attempts remain; voice calls are counted in `VoiceHeld` and never cancelled; `Done` when idle. Grace <= 0 -> 5 min default, capped at 1 h. Active or unknown state is a no-op (cancel is not fail-safe on unknown input; admission is already blocked by `Evaluate`).
- `apps/gateway/internal/nodes/ramp.go`: `Ramp{Limit, Good}.Step(sample, pressure, active, maxN)`. New helper starts at 1; +1 per `RampSamples` (8, = 2 min of heartbeats) consecutive healthy samples (CPU < 60%, mem avail > 25%, pressure not reduced) while `active >= limit`; any other sample resets the run; earned limit clamped to `maxN`; `maxN < 1` holds.
- `apps/gateway/internal/nodes/telemetry.go`: `SampleFromCapacity(cpuTotal, cpuUsed, memTotal, memUsed)` maps the existing `ReportCapacityResponse` fields to a `PressureSample`; unusable input fails closed to a worst-case sample (can enter pressure, never recover). `WorstSample` combines cgroup and host-wide readings.
- `apps/gateway/internal/nodes/drain_test.go`: table tests for all of the above.
- `docs/adr/0009-helper-grant-shrink-drain-ramp-telemetry.md`: the decision.

## Deviations

- Telemetry source: the helper proto has only one set of cpu/memory used/total (read as the helper's cgroup budget). A separate host-wide pressure reading is not in the proto; adding fields needs a contract change plus regenerated bindings (no protoc here), so only the combining helper (`WorstSample`) ships. Contracts-first follow-up below.
- `Ramp` has no persisted `Good` counter: `HelperState` (P4.4) stores only `RampedLimit`, and no migration was added. A restart restarts the current run, which is the conservative direction.
- Revoked grants reuse the draining grace (a revoked helper is usually unreachable, so the cancel path is advisory); voice is never cancelled in either case.
- Ramp has no step-down; pressure halves admission via `AdmissionLimit` instead (`ponytail:` comment).

## Follow-ups

- Placement/poller caller (P4.15 and later) must call `Ramp.Step` per heartbeat with `min(grant max, ceiling)` as `maxN`, call `ShrinkCap` on every limit change, persist `Ramp.Limit` into `HelperState.RampedLimit`, record the drain start, and perform the Drain RPC and cancels.
- Optional contract addition: host-wide cpu/memory fields on `ReportCapacityResponse`.
- Voice calls held past a revoke need an operator decision path (UBAG never terminates them here).
