# P6.6 - Conversation-hot warm resume fast path

Status: **partial**. The fast path is built, tested with fakes and merged OFF. It is NOT evidence-justified and NOT live-verified:
the slice is conditional on P0.13/P0.9 showing a win, and P0.13 produced no baseline (see P0.13.md), so the "drop if no win" gate is
unevaluated. A human must verify against the live DOM before anyone enables the flag.

## Files
- `apps/worker/ubag_worker/live/daemon.py`: `WarmWorkerDaemon._resume_in_place` + one call in `_checkout`.
- `apps/worker/ubag_worker/live/page_driver.py`: new concrete `PageDriver.can_resume_in_place(selectors, thread_ref)` (default `False`),
  overridden in `MockPageDriver` and `PlaywrightPageDriver`.
- `apps/worker/tests/test_warm_reuse.py`: `TestWarmResumeFastPath`.

## Flag
`UBAG_WARM_RESUME_FASTPATH` (default off; truthy = `1/true/yes/on`). No migrations, no contract changes.

## Behaviour
In `_checkout`, after the warm-key lookup (tenant, provider, profile already match), when the flag is on AND the job carries a
`conversation.key` with a non-empty `thread_ref` AND `driver.can_resume_in_place(...)` is true, `prepare_for_next_job` (new-chat click,
emptiness wait) is skipped. `can_resume_in_place` on the live driver requires a live page, `page.url == thread_ref` (exact string) and no
periodic reload due (it still counts the job toward `UBAG_WARM_RELOAD_EVERY`, so the memory bound holds). Anything else, including any
exception, runs the full gate exactly as today. `clear_attachment_state` still runs. The engine still calls `resume_thread` (goto + prior-turn
confirm), so the saving is the new-chat click, the emptiness wait and the navigate-away; the goto and the up-to-20 s confirm are NOT removed
(deliberately conservative until live-verified).
