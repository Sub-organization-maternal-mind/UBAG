# P4.2 - Attempt ledger with lease generation and fenced commits

Status: merged (see PR). Inert: nothing in the gateway calls the ledger yet; the helper plane (P4.x) is the first consumer. Memory and Postgres stores; SQLite fails closed.

## What landed
- `apps/gateway/internal/jobs/attempts.go` (contract, own commit): optional `AttemptStore` capability (same pattern as `MetricsStore`/`RecentEventLister`), `Attempt`, `AttemptRef{JobID, AttemptID, Generation}`, `BeginAttemptRequest`, the error vocabulary, and the rules as pure functions (`planBegin`, `fenceAttempt`, `validateAttemptCommit`) so both stores obey one rule set.
  - `BeginAttempt` - compare-and-set on `ExpectedGeneration` (0 for the first attempt); the new attempt takes `ExpectedGeneration+1` only if that is still the next generation. Serialized per job by the job-row lock (Postgres) / the store mutex (memory). Replaying the same request returns the active attempt unchanged; reusing an attempt id with other parameters is a conflict. A still-held lease is a conflict; a lapsed active predecessor is marked `expired` in the same transaction.
  - `RenewAttempt` - extends the lease to now+ttl, never shortens it (`GREATEST`). `MarkSubmitted` - sets the submission boundary once (idempotent, first timestamp wins).
  - `CommitEvents(ref, events)` - applies the batch exactly as `ApplyWorkerEvent` would, but only if `ref` is the job's active attempt at the presented generation; all-or-nothing (Postgres transaction; memory snapshot/rollback). A terminal result closes the attempt (`finished`). Replays are no-ops (worker event key dedupe), including a replay against a `finished` attempt (lost ack, job already terminal).
  - `ExpireAttempts(limit)` - marks lapsed active attempts `expired` and returns them (oldest first, bounded). `ListAttempts(job)` - ascending generation.
- Error vocabulary: `ErrAttemptFenced` is the umbrella for "your write was rejected" (`ErrAttemptStale` = generation mismatch, `ErrAttemptInactive` = attempt expired/finished). Others: `ErrAttemptNotFound`, `ErrAttemptConflict` (lost the CAS, lease held, id reused), `ErrAttemptFingerprint`, `ErrAttemptSubmitted`, `ErrAttemptJobTerminal`, `ErrAttemptInvalid`, `ErrAttemptEventMismatch`.
- `memory_attempts.go`, `postgres_attempts.go`: the two implementations. `memory.go` / `postgres.go`: `checkWorkerEvent`, `checkWorkerEventAgainstJob` and the per-event apply step (`applyWorkerEventLocked`, `applyWorkerEventTx`) extracted from `ApplyWorkerEvent` so `CommitEvents` shares them. `ApplyWorkerEvent` behaviour, return values and error paths are unchanged (existing jobs tests pass).
- `migrations/postgres/0022_gateway_job_attempts.sql`: `gateway_job_attempts` (PK `(job_id, attempt_id)`, `UNIQUE (job_id, generation)`, FK to `gateway_jobs` with cascade, partial unique index `uq_job_attempts_active` = at most one live lease per job, partial expiry index). Additive and idempotent. This is the only attempts table; the node store (P4.4) must reference it, not define a second one.
- `serve.go`: `configureExecutorAttempts` right after the stores are built.

## Semantics worth knowing
- Lease expiry is liveness, not the fence. A lapsed but unsuperseded, unreaped attempt can still renew and commit (nothing has taken over, so accepting its finished work is safe). The fence closes when `BeginAttempt` supersedes it or `ExpireAttempts` reaps it; both flip the row to `expired` atomically, after which every write from it is rejected. A reaper (P4.18) must therefore call `ExpireAttempts` before deciding the job's fate.
- A fenced writer is told so with `errors.Is(err, ErrAttemptFenced)`; that is a normal lost-lease outcome, not a store failure.
- D4 guard: once an attempt crossed the submission boundary (`MarkSubmitted`), `BeginAttempt` refuses a successor (`ErrAttemptSubmitted`) unless the caller sets `AllowAfterSubmitted` after verifying the provider never received the prompt. The job should instead end `failed` with `submitted=true` and `reconcile_required` (P4.18).
- Input fingerprint is pinned across attempts of a job (`ErrAttemptFingerprint`), per ADR-0007.
- Attempt ids must match `^att_[A-Za-z0-9]+$` (<=128), the helper proto / worker schema convention. The P3.7 local attempt id (`lease.LeaseID()`) does not and is not used with the ledger.
- Events committed through a ref must be for that job and, when stamped with `data.attempt_id`, by that attempt (`ErrAttemptEventMismatch`).
- Bounds: lease TTL 0 means 120 s (ADR-0007), max 15 min; <=256 events per commit; sweeps <=1000.
- Lock order (no cycles): job row, then attempt rows; `RenewAttempt`/`MarkSubmitted`/`ExpireAttempts` touch attempt rows only and the sweep uses `SKIP LOCKED`.
- Lease times use the gateway clock (`p.now`), like the other stores; replicas are expected to share NTP time.

## Deviations
- SQLite has no ledger and no migration; the spec's `migrations/sqlite/0014` and `sqlitestore/schema.sql` / `migrate.go` edits are intentionally not done because the deliverable says sqlite fails closed. `sqlite_cas_test`/`sqlitetest` parity is therefore replaced by the startup refusal test.
- No `DispatchEnvelope.Attempt` generation/expiry fields (P3.7 had said they would join here): nothing sets them yet and the fence rides the helper `Fence` (P2.3). The stale comment in `executor.go` was corrected.
- The ledger names are `RenewAttempt` / `ExpireAttempts` (spec: Renew / Expire) to stay unambiguous on a type that also implements `Store`.
- `ListAttempts` is an addition beyond the five spec operations (a dispatcher needs the latest generation for the CAS; the reconciler and tests need history).

## Follow-ups
- P4.x helper dispatch: `BeginAttempt` before `RunAttempt`, `RenewAttempt` on the 20 s cadence, `CommitEvents` for streamed events, `ExpireAttempts` sweeper.
- P4.18 reconcile: on an expired attempt with `Submitted()`, end the job `failed` with `submitted=true` + `reconcile_required`; otherwise retry with the next generation.
- A job cancelled/terminalised through `UpdateStatus` leaves its attempt `active` until a later commit or sweep closes it; harmless (commits are no-ops on a terminal job) but the sweeper may want to skip attempts of terminal jobs when reporting.
- Retention: attempts cascade with their job; no separate pruning.
