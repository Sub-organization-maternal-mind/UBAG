# P2.7 - SSE and gRPC stream resume and close semantics contract

Status: merged (contract, fixture and docs only; the gateway does not implement resume yet - that is P3.13).

## Contract (additive; a request with no cursor behaves exactly as before)
- `GET /v1/sse/jobs/{job_id}` (packages/openapi/openapi.yaml): documents frame format, per-job strictly increasing gateway-assigned `sequence`, at-least-once delivery with dedupe by `event_id`, resume via `Last-Event-ID` header and/or `after_sequence` (effective cursor = larger of the two; unknown `Last-Event-ID` ignored; malformed `after_sequence` = 400), HTTP 204 when the cursor is at or past the terminal event, optional close after the terminal event, tokens provisional until a terminal event. New documented params: `after_sequence`, `Last-Event-ID`, `snapshot` (already accepted by the handler, previously undocumented); new responses 204 and 400.
- `jobs.proto`: comments only (no wire change) on `StreamJobEvents`, `ListJobEventsRequest.after_sequence`, `JobEvent.sequence`: same semantics, cursor is `after_sequence`, OK completion after the terminal event, OK with no messages when resumed at or past it.
- `job-event.schema.json`: `sequence` description now states gateway-assigned, strictly increasing, resume cursor, at-least-once.
- `listJobEvents` description states the increasing order and points to the SSE semantics.

## Deviations / notes
- Today's gateway ignores `Last-Event-ID` and `after_sequence` on the SSE route and replays from sequence 0; it also never closes the stream after a terminal event (it pings until the 10 min TTL). The contract says so in the OpenAPI text; replay-from-start stays conformant for clients that dedupe by `event_id`. P3.13 implements resume, 204 and close-on-terminal.
- The one visible default change once P3.13 lands: an EventSource that reconnects now resumes instead of replaying from 0, and gets 204 after a terminal event. That is the intended fix; clients that dedupe by `event_id` see no difference.
- Worker-side sequences can repeat across attempts (see worker-daemon/v2.json); the delivered `sequence` is the gateway store's per-job number, so strict increase holds for delivery.
- No SDK helper change: `parseSseChunk`/`streamEvents` already stop at the first terminal event.
