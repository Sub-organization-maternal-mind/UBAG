# P3.11 Batch event apply, one notify per batch, token coalescing, byte budget

Status: merged (Go gateway only; no contract change; the streaming behaviour stays behind `UBAG_WORKER_STREAM_INGEST`, default off; memory and SQLite exercised, Postgres written but not run).

## What landed

- **`Store.ApplyWorkerEvents(ctx, events) (Job, bool, error)`** on the `Store` interface, implemented for memory, SQLite and Postgres. 1..`MaxAttemptCommitEvents` (256) events for ONE job apply atomically: one lock (`FOR UPDATE` on Postgres), one commit, one waiter wake (only when something changed; a replayed batch wakes nobody). Each event follows `ApplyWorkerEvent`'s rules (dedupe key, terminal drop, payload validation, trace/api-version match), so duplicates and out-of-order sequences are no-ops or arrival-ordered exactly as one at a time. A failing event rolls the whole batch back, dedupe keys included. A missing job is `found=false`, no error. Shape errors (empty, mixed jobs, no type, too many) fail before the store is touched (`validateEventBatch`).
  - Memory: `applyBatchLocked` (extracted from `CommitEvents`, which now uses it) gives the all-or-nothing rollback.
  - SQLite: `ApplyWorkerEvent` is now `ApplyWorkerEvents` of one event; the per-event body moved into `applyWorkerEventTx` (mirrors Postgres). Same observable behaviour for single events.
  - Postgres: loops the existing `applyWorkerEventTx` in one transaction (the same helper `CommitEvents` uses).
- **Streaming sink batches and coalesces** (`executor/streamingest.go`). Non-terminal events are buffered and written with `ApplyWorkerEvents`. Token deltas inside the flush window merge into one token event (text concatenated up to 16 KiB, id/sequence/`token_index` of the first, `data.coalesced_deltas` = deltas merged). Flush rules: the first token after a quiet period is written at once (time to first token unchanged); any non-token event flushes at once; 64 pending events flush; a timer flushes a trailing token; the run's end (clean or not, `runWorker`) flushes before the terminal is applied or the failure recorded, so history is in the worker's order and the tokens of an abandoned attempt still land as its partial.
- **Per-attempt byte budget** replaces the 512-event / 1 MiB caps for streams. Every delivered event (stale and telemetry included) costs its JSON data size + 256 bytes; over the budget the attempt fails with ingestion class `over_budget`. Never truncates. The batch path keeps its caps.
- The held-terminal rule is unchanged: the terminal is never applied during the run, and only a clean `JOB_END` with exactly one terminal lets `finish()` hand it back (the P1.1 false-truncation guarantee, re-run below with the flag on).

## Deviations and notes

- Added `ApplyWorkerEvents` to the `Store` interface rather than an optional capability: only the three in-repo stores implement `Store`, so nothing else breaks.
- Coalescing is on the gateway sink, not the store: the store stays a faithful log of what it is handed. The worker's own tail coalescing (`UBAG_WORKER_STREAM_MAX_TOKEN_EVENTS`, default 400, P3.8) is untouched.
- A coalesced token keeps the FIRST delta's event id; a replay after a retry is protected by attempt-scoped ids (P3.10), not by id stability across different coalescing.
- The timer flush uses the last `Emit` context; a failure is parked and reported by the next `Emit` or the run's final flush.
