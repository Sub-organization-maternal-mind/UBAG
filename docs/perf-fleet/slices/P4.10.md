# P4.10 - Streamed, checksummed asset staging

Status: merged as a library + handler. Inert: no flag is read and nothing mounts the handler yet (it needs the attempt keypair and an HTTPS mount on the `UBAG_HELPER_PLANE` listener, both later wiring). Consumer flag ladder: `UBAG_HELPER_PLANE` < `UBAG_HELPER_DISPATCH`.

## What landed
- `apps/gateway/internal/helperapi/assets.go` (new): `Assets`, an `http.Handler` for `GET|PUT /assets/<key>`.
  - Layers: mTLS node identity (`Assets.Authn`; `AuthnFromAuthenticator` re-verifies the client cert per request) -> attempt token (`attemptcap.Peek` for the job, then `attemptcap.Authorize` against the LIVE attempt row with the job's tenant, the mTLS node, the key and the op) -> manifest.
  - The job id is the token's, never the URL's, so another job's artifacts cannot be addressed. Tenant is bound in the handler (ArtifactStore has no tenant parameter): token tenant must equal the loaded job's tenant.
  - Manifest: a get must name a key in `attachments.DeclaredAttachments(job.Input)`; a put must NOT name one (declared inputs are immutable) and must carry `X-Ubag-Asset-Kind` in `attachments.ValidKind`, a valid content type, `Content-Length`, and `X-Ubag-Sha256`.
  - Every denial (bad/expired/forged token, wrong node or tenant, fenced or reaped attempt, wrong op, key outside token or manifest, unknown key, bad key syntax, other method) returns the identical 404 body `UBAG-HELPER-ASSET-NOT-FOUND-001`.
  - Get: serves `Content-Length` and `X-Ubag-Sha256` from the `ArtifactRecord`, streams while hashing, and aborts the stream (`http.ErrAbortHandler`) if size or digest does not match; a record without a 64-hex checksum is a 500 integrity error (fail closed); over `MaxBytes` (default 32 MiB, the public upload cap) is 413.
  - Put: size cap by declared length and by `MaxBytesReader`; body hashed while stored; on size/digest mismatch (header vs bytes vs store record) the artifact is deleted and 422 returned; an existing key is 409.
- `apps/gateway/internal/helper/staging.go` (new): `StagingClient` (Get/Put over a caller-supplied mTLS `http.Client`), a `verifyingReader` that returns `ErrIntegrity` instead of EOF on a short/long/wrong-digest stream, and `ReadOnlyStore`, an `artifacts.ArtifactStore` that only serves `GetArtifact` for its own job (Put/Delete/List return `ErrReadOnly`).
- `executor.ProcessWorkerRunner.MaterializeAttachments`: exported wrapper over `materializeAttachments`, so the helper reuses it with `Artifacts: ReadOnlyStore{...}`; the `ubag-attach-` temp prefix the worker path guard needs stays in one place.
- `attemptcap.Peek`: signature/typ/aud/shape/expiry check returning claims, used only to learn which job to load before `Authorize`.
- Public attachment manifest, REST and proto contracts unchanged.

## Not run
Real mTLS handshake against this handler (identity is injected in tests; `helperauth` has its own TLS tests), full gateway suites, Postgres-backed attempt store.

## Deviations
- The proto `StageManifestResponse.staging_path_prefix` describes a helper-side upload endpoint (primary pushes). This slice follows the roadmap deliverable instead: the helper pulls from, and pushes outputs to, the primary under an attempt token. The proto is unchanged.
- No wiring in `serve` (no HTTPS mount on the helper plane listener, no attempt keypair loading, no audit emission): both depend on slices that have not landed.
- Put is check-then-write, not atomic (marked `ponytail:`); the token already limits who may write the key.
- A failed-verification put is deleted after the store write because `ArtifactStore` has no staging area.
