## Analysis (from code reading at the current tip, not measured)
Every Postgres call on the accept path checks a connection out of the single 20-open pool. For one `POST /v1/jobs` (Postgres store, shared admission live):

| Step | Code | Pool checkouts | Round trips / notes |
|---|---|---|---|
| authz audit (`job:create`, outcome `allow`) | `emitAuthorizationAudit` -> `audit.PostgresStore.Append` | 1 | BEGIN, `pg_advisory_xact_lock(hashtext(tenant))`, SELECT head, INSERT, COMMIT. **Serialised per tenant; the connection is held while queued on the lock.** Only `*:read` allows are skipped. |
| idempotency reserve | `idempotency.PostgresStore.Reserve` | 1 | tx: BEGIN, upsert/load, COMMIT |
| admission acquire | `SQLTokenBackend.AcquireToken` | 1 | tx: BEGIN, advisory lock on EVERY lane (taken inside the lane loop, `admission_sql.go` AcquireToken), cap read, live-count per lane, INSERT token, INSERT per lane, COMMIT |
| job create | `jobs.PostgresStore.Create` | 1 | BEGIN, `nextval`, INSERT job, INSERT event, COMMIT (5) |
| admission associate | `AssociateToken` | 1 | 1 UPDATE |
| idempotency complete | `Complete` | 1 | 1 UPDATE |

So a create makes at least 6 sequential pool checkouts and roughly 25 round trips; release of the admission token (4 round trips) happens later at job end. 2890 waits over 15.95 s is about 5.5 ms of average wait per wait event.

Correction after review (the first draft of this analysis ranked the audit lock first; the benches did not support that). A reviewer ran the merged benches plus a scratch composite on a throwaway local PG18 (100 clients, open=20, loopback, NON-AUTHORITATIVE, reviewer-reported, not reproduced here). Full accept path 1.60-1.62 ms/op; without the audit append 1.56-1.60 (no change); removing admission halves it (0.82-0.84); removing all three of audit, idempotency and admission leaves 0.32-0.36. Single-store: admission acquire+release on one lane 1.64-1.77 ms, audit append 0.68-0.77. The pool sweep supports "a bigger pool cannot lift p95": composite ns/op is flat or worse as open grows (about 1.44-1.68 ms at 5, 2.1-2.7 at 100). The earlier admission bench used three lanes (3x lock count, 2.78-3.35 ms/op) although production runs ONE lane (the tenant and global lanes exist only when `UBAG_ADMISSION_MAX_INFLIGHT_*` is set; the VPS compose passes them empty); it now defaults to one lane. Use `BenchmarkPostgresCreatePathComposite` with `UBAG_BENCH_SKIP` to confirm the split on the lab host.

Hypotheses to confirm with the benches and pprof, in order of the evidence above:
1. **The pool wait is a symptom of lock queues on a single tenant, not of an undersized pool; the shared-admission dynamic-lane lock is the leading suspect, the per-tenant audit advisory lock is not.** All same-tenant clients queue on the same dynamic lane lock inside `AcquireToken` (about 7 round trips) while holding a pool connection; the audit append (`pg_advisory_xact_lock(hashtext(tenant))`) is a second, smaller serialisation point. With one tenant (the acceptance-harness shape, also the single-tenant production shape), up to 20 pool connections can be parked inside `pg_advisory_xact_lock` waiting for the one append in progress, while every other step of every other request waits in `database/sql` for a free connection. Raising `UBAG_DATABASE_MAX_OPEN_CONNS` would then only move the queue into Postgres (more sessions blocked on the same locks, more `max_connections` pressure) and cannot lift accept p95. Smaller pools may even look better.
2. With `GOMAXPROCS=1` on a 1 CPU gateway the Go side (pgx encode/decode, JSON, SSE, TLS) competes for the same CPU as the connection hand-offs; a pool larger than one CPU can drive gives no throughput.
3. Round-trip count per create (about 25) times the gateway-to-Postgres latency sets the per-request floor; a latency-bound p95 target can be unreachable regardless of pool size.

## Not landed, deliberately (each needs a measured before/after: "land only measured wins")
- Pool resize: no data. Prod defaults stay 20/5 (deploy examples already differ per profile: 5/2, 10/5, 25/10).
- Audit-append decoupling for `*:create` allows (async/batched append): NOT recommended. It changes durability/ordering semantics of the Merkle audit trail and the composite A/B above shows removing the audit append buys no throughput. Revisit only if a lab-host composite A/B shows a gain. The admission lane lock (shorter transaction, fewer round trips under the lane lock) is the first candidate to measure instead.
- Fusing `nextval` into the job INSERT (saves 1 of 5 round trips in the create tx): safe but unmeasurable without Postgres here.

## Runbook (isolated stack, never the shared VPS)
```
# 1. bench each store at 100 clients, sweep pool size (throwaway Postgres with repo migrations applied)
export UBAG_TEST_POSTGRES_DSN=postgres://...   # throwaway DB only: the benches refuse a non-loopback/private host
# (unless listed in UBAG_BENCH_ALLOW_HOST) and a database name without "bench" or "test"; audit rows are append-only (WORM)
cd apps/gateway
for open in 5 10 20 40; do
  UBAG_BENCH_POOL_OPEN=$open UBAG_BENCH_POOL_IDLE=$((open/4+1)) \
    go test ./internal/jobs ./internal/idempotency ./internal/audit ./internal/topology \
      -run '^$' -bench 'Postgres(Create|ReserveComplete|AppendOneTenant|AdmissionAcquireRelease)' -benchtime 2000x -count 3
done
# Read ns/op and poolwait-ms/op per store. Then A/B the composite to see which lock matters:
#   -bench PostgresCreatePathComposite                         (full path)
#   UBAG_BENCH_SKIP=audit ...   UBAG_BENCH_SKIP=admission ...   UBAG_BENCH_SKIP=audit,idempotency,create ...
# The component whose removal cuts ns/op most is the bottleneck; if poolwait-ms/op does not fall as open grows, hypothesis 1 holds.

# 2. end to end: gateway with UBAG_PPROF_ADDR=127.0.0.1:6060 under the P0.13 matrix step clients-100
node tools/perf/baseline-matrix.mjs run --i-understand-this-is-load ...
go tool pprof -seconds 30 http://127.0.0.1:6060/debug/pprof/profile
# Go goroutine dumps carry function names, not SQL text, so count frames, not 'pg_advisory':
curl -s 'http://127.0.0.1:6060/debug/pprof/goroutine?debug=2' > g.txt
grep -c 'audit.(\*PostgresStore).Append' g.txt                  # sessions in the audit append
grep -c 'topology.(\*SQLTokenBackend).AcquireToken' g.txt       # sessions in the admission acquire
grep -c 'database/sql.(\*DB).conn' g.txt                        # still waiting for a pool connection (not holding one)
# Frames above minus 'DB.conn' waiters = holders blocked on the lock. Or sample the database instead:
#   SELECT count(*) FROM pg_stat_activity WHERE wait_event_type='Lock' AND wait_event='advisory';
# Compare ubag_db_pool_wait_total / ubag_db_pool_wait_seconds_total before and after each UBAG_DATABASE_MAX_OPEN_CONNS value.
```
Only the three-way comparison (bench, pprof, harness accept p95) justifies a change. If accept p95 <= 200 ms at 100 clients stays unreachable on 1 CPU / GOMAXPROCS=1 after the audit/round-trip fixes, the recommendation is to resize the gateway CPU (not the pool) and record the evidence here; do not resize prod from this slice.
