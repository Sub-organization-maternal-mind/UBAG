## Results (NON-AUTHORITATIVE: Windows dev box, Xeon E5-2695 v4, 36 threads, `-benchtime=300x`)

Command: `go test -run '^$' -bench 'Spool|RunOnce|Daemon' -benchtime=300x -benchmem ./internal/executor`

| Benchmark | ns/op | allocs/op |
|---|---|---|
| SpoolEnqueue terminal=0 | 5.6 ms | 252 |
| SpoolEnqueue terminal=1000 | 8.3 ms | 1263 |
| SpoolEnqueue terminal=10000 | 41.0 ms | 10278 |
| SpoolLeaseNext terminal=0 | 2.63 ms | 354 |
| SpoolLeaseNext terminal=1000 | 2.67 ms | 354 |
| SpoolLeaseNext terminal=10000 | 2.94 ms | 354 |
| RunOnce (WorkerRunFunc, memory store) | 6.07 ms | 608 |
| DaemonLineProtocol 2 events | 46 us | 59 |
| DaemonLineProtocol 50 events | 378 us | 981 |

Finding: the hypothesis is CONFIRMED. Enqueue cost grows with the terminal-file count (about 7x at 10k; allocations grow roughly one per terminal file) because `EnqueueJob` -> `jobExistsInAnyState` -> `findJobPath` runs a `filepath.Glob` over done/failed/cancelled on every enqueue. LeaseNext is flat (it only reads `pending/`). This is the control for P1.4; the fix (indexed or cached existence check) is not part of this slice. Windows NTFS numbers overstate absolute cost versus the Linux VPS; compare ratios only.

`measure_slots.py` (stub daemon, protocol overhead only, 10 events at 100 ms, psutil): RSS about 17.4 MiB per slot (1 slot 17.4, 2 slots 35.5, 4 slots 70.7 MiB), first-event latency about 101-102 ms (= the stub's first sleep, so framing overhead is below measurement noise), CPU negligible. Idle/warm/mid-stream RSS are equal for a stub, as expected.
