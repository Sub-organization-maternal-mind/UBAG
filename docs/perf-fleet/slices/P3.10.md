# P3.10 Daemon streaming ingest: provisional until one valid terminal

Status: merged (Go gateway only; flag default OFF; memory and SQLite stores exercised, Postgres not run).

## What landed

The consumer now ingests a warm-daemon job as a stream behind `UBAG_WORKER_STREAM_INGEST`. Streamed events are PROVISIONAL until one valid terminal:

- **Non-terminal events are applied immediately.** `streamIngest` (new, `executor/streamingest.go`) is the `EventSink` the consumer hands to `StreamWorker`. Each event is stale-attempt filtered, normalized (job/api/trace checks, same as the batch path), and applied with `Jobs.ApplyWorkerEvent` as it arrives, so a reader sees tokens while the daemon is still running. The post-apply projections (manual-action alert, login state) run live too.
- **Telemetry intercepts still run on the stream path.** `concurrency.cap_changed`, `browser.topology_reported`, `conversation.thread_*` and `session.new_chat` / `session.configured` / `file.attached` are consumed by `handleTelemetryEvent`, extracted from `RunOnce` so the batch loop and the sink share one copy. They are never applied as job events, before or after the terminal.
- **The single terminal is HELD.** It is never applied while the run is in flight. Only after the runner reports a clean end (the daemon's `JOB_END` with status completed) with exactly one valid terminal does `finish()` hand it back, and the unchanged batch ingestion applies it (so completion, result, `finishTerminalIngestedJob`, stage timings and the lease finisher are the existing code).
- **Anything else abandons the attempt.** A daemon killed mid-stream, a stream without `JOB_END`, a failed `JOB_END`, zero terminals, two terminals, an invalid event, an over-bound stream or a store error returns an error from the run; the held terminal is dropped, the tokens already applied stay in the history as that attempt's discarded partial, and the consumer appends the usual failure event via `applyFailure`. The job can never complete on a truncated or ambiguous stream.
- **Streaming implies attempt-scoped event ids.** `RunOnce` sets `envelope.Attempt` when the job streams, even without `UBAG_WORKER_ATTEMPT_EVENT_IDS`. Without it a job re-leased after a streamed partial would re-emit legacy `job:seq` ids that collide with the abandoned attempt's applied events and be silently dropped by the store (this is the collision regression the roadmap named). Events stamped with another attempt's id are dropped per event.
- **Serve router.** `targetWorkerRunner` (the production runner) implemented only `RunWorker`, so P3.9's `StreamingWorkerRunner` assertion never matched and the flag would have been inert in production. It now implements `StreamWorker` and an optional `StreamsJob(envelope)` selector (new `streamSelector` in the executor): warm-daemon jobs stream (through a single daemon or a `DaemonPool`), per-job worker targets (mock, generic) and voice control jobs stay on the batch path.

Behaviour with the flag off is unchanged: `streaming` is false, `ingest` is nil, and the only edits on that path are the extracted helpers (`handleTelemetryEvent`, `afterEventApplied`, `staleAttemptEvent`).

Failure typing under `UBAG_WORKER_STRICT_SUBMIT` works on the stream path: the runner types its own errors from the in-process `prompt_submitted` marker, and the sink types the ingestion errors it raises (and the consumer carries the sink's sighting into the ambiguity check for failures after the run). A post-submit failure ends `failed_terminal` with `submitted` and `reconcile_required` and is never replayed.

## Flags

| Flag | Default | Notes |
|---|---|---|
| `UBAG_WORKER_STREAM_INGEST` (Go) | off | Only read by the consumer; only affects runners that stream (the warm daemon). Logs one warning when it runs without `UBAG_WORKER_STRICT_SUBMIT`. |
| `UBAG_WORKER_STREAM_EVENTS` (Python), `UBAG_WORKER_STRICT_SUBMIT` | off | Not new. Pair them: without STREAM_EVENTS the worker buffers its events (ingest still works, nothing is live); without STRICT_SUBMIT an interrupted job can still be replayed from the queue. |

Migrations: none. No contract change: `job-event.schema.json` already documents provisional token events, `attempt_id`, `submitted` and `reconcile_required` (P2.2).

## Deviations

- The work item listed `executor.go`, `jobs/memory.go`, `jobs/sqlite.go` and `jobs/postgres.go` and the contract items `DispatchAttempt{id,lease_generation,expires_at}` and an attempt-scoped `event_key`. None needed a change here: P3.7 already carries `DispatchAttempt{ID}` and the worker derives attempt-scoped event ids, the stale-attempt filter is in-process, and lease generation / fencing arrive with the attempt ledger (P4.2, P4.9). The stores are untouched.
- The per-attempt byte budget that replaces the 512-event / 1 MiB bounds is not here: it belongs to P3.11 (batch apply, coalescing, budget). The bounds stay, and an overrun fails the attempt (never a silent truncation). The Python side caps live token events at 400 (P3.8) to stay under the 512.
- Streaming implies attempt-scoped ids rather than requiring `UBAG_WORKER_ATTEMPT_EVENT_IDS`; it does NOT imply `UBAG_WORKER_STRICT_SUBMIT` (BINDING keeps the flags independent): it warns once instead.
- Events that follow the held terminal and are not telemetry are ignored (the store drops them for a finished job too). Telemetry that follows it still runs live, so a conversation bind or concurrency report can be recorded for an attempt that is later abandoned; those describe real provider/browser state, not the attempt's result.
- Added the `streamSelector` capability and the serve router's `StreamWorker` (P3.9 left the router batch-only, which made the flag inert in production); added `UBAG_WORKER_STREAM_MAX_TOKEN_EVENTS` to the worker env allowlist (P3.8 added the tunable but nothing forwarded it); compose, `env.example` and the VPS README were edited so the three flags can reach the container.
- Metrics: worker-run duration includes the incremental applies; ingestion duration is the time spent applying (plus the tail), and the event count is the whole stream. Ingestion failure classes match the batch path.

## Follow-ups

- Backpressure: a slow store slows the daemon's stdout reader. P3.11 (batch apply, one notify per batch, coalescing) is the fix.
- D4 on the Go side: a Go-side deadline (`runCtx` timeout) or a daemon-side deadline kill still ends the job `failed` ("timed out" message), not `timed_out` with `data.partial`. That needs the proto:2 handshake and a `stream_end_reason` on the gateway-synthesised failure; abandoned-stream failures do not yet carry `stream_end_reason` or the abandoned attempt's partial.
- The attempt id is the queue lease id, which does not match the documented `att_` pattern and is not unique for the NATS fallback (`"nats"`); worth fixing before the attempt ledger replaces it (P4.2).
- Only the warm daemon streams. The process runner stays batch (P3.9 decision); if production runs `UBAG_WORKER_DAEMON=false` this flag changes nothing (roadmap conflict 13).
- P3.5: read the daemon `hello` features and only expect live lines when `stream_events` is advertised.
- Run the two pool tests above in CI under load; consider a deterministic clock for the LRU tie-break.
